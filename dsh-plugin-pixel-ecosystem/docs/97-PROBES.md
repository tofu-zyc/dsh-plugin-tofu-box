# 97 · 行为探针与测试门禁

> 这份文件回答两个问题：**探针每个数字怎么读**、**读到多少算过关**。
> 没有这把尺子，任何行为/能量改动都只能靠“看起来还行”来验收，`90-ROADMAP.md` 的门禁也就无从判定。

## 0. 一句话

`node tools/behaviour-probe.mjs --seed 12345 --seconds 900` 出一条可比的报告；改行为/能量前后的两条报告必须**同 seed、同 bundle 口径**贴在一起比对。

## 1. 怎么跑

```powershell
cd dsh-plugin-pixel-ecosystem
node tools/behaviour-probe.mjs --seed 12345 --seconds 900
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--seed N` | 12345 | 世界种子。**对比必须同 seed**，否则差异是噪声。 |
| `--seconds S` | 900 | 模拟秒数（1× 口径）。900 s = 7.5 个游戏日（`DAY_SECONDS=120`）。 |
| `--width` / `--height` | 引擎默认 | 覆盖地图尺寸。P0-5 放大到 1024×640 后，跨版本对比要显式给旧尺寸。 |
| `--no-immigration` | 移民开 | 关掉移民安全网。测“链路本身能不能自持”时用；测玩家体验时别关。 |
| `--sample-every N` | 10（=1 s） | 能量/年龄/生产者的采样间隔（tick）。降精度换速度。 |
| `--top N` | 6 | 每个物种列几个意图。 |
| `--json` | 关 | 机器可读报告，用于 before/after 数值 diff。 |
| `--help` | | 用法。 |

退出码：`0` 正常；`2` 参数错误；`3` bundle 起不来（此时**先修 bundle**，不要怀疑引擎数值）。

## 2. 先看报告头三行

### 2.1 `bundle <sha1前12位> (STALE: ...)`

探针对 `client.js` 取 sha1。**两条报告只有 hash 相同才可比**。带 `STALE` 说明 `src/parts` 已经改过但没跑 `node tools/build-client.mjs`——这时报告度量的是旧 bundle，不是当前工作区。

### 2.2 `throughput`

- `ticks/s wall`：整条探针（含采样开销）的吞吐。**玩家体验对应这个数**。
- `ticks/s sim only`：只统计 `stepWorld`。和 wall 的差距 = 探针自身开销；差距过大说明探针写得太重，不代表引擎慢。

门禁（`90-ROADMAP.md` P1-5）：**≥ 30 ticks/s @ 3000 实体**。8× 播放需要 ≥ 10 ticks/s，所以验收线是 3× 余量。
当前 `tests/balance.test.mjs` 卡的是 >80 ticks/s（8× 预算的 8 倍余量）。

### 2.3 `engine generation legacy -> intent=... | reserve=... | hunger=... | cause=...`

这一行是**探针的降级证据**，不是装饰：它打印的是这次运行**实际读到**的字段，不是“理论上支持”。

| 指标 | 能量账本（0.3.x） | 旧引擎（0.2.x） |
|---|---|---|
| `intent` | `state.id` | `intent` |
| `reserve` | `body.E / body.Emax` | `energy / balance.maxEnergy` |
| `hunger` | `drives.hunger` | `needs.hunger` |
| `cause` | `body.cause` | `inferred`（推断，见 §6） |

看到 `generation legacy` 就说明这次跑的是旧引擎：**死因是推断值，`cause` 那一列的可信度按 §6 打折**。

## 3. 指标逐条：怎么读 / 阈值

### 3.1 时间预算（意图 × 时长）

`rabbit rest 69.6%(127996s) forage 21.6%(39621s) ...`

- **含义**：该物种全部个体的**实体-时间**里，有多少落在各个意图上。百分比的分母是该物种的 `entity-seconds` 总和（不是墙钟时间）。
- **怎么读**：这是“这个物种一天到晚在干什么”的唯一直接答案。`rest` 占比就是“发呆率”。
- **阈值**：`rest` 占比 **< 35%**（`90-ROADMAP.md` P2 门禁 1，旧版 0.2.x 是 69%）。
- **陷阱**：分母很小时（刚投放、刚出生）百分比会很极端，所以同时看绝对秒数。

### 3.2 意图驻留（中位数/均值）与决策抖动

`rabbit rest 1.0/3.3  forage 0.5/1.2   switches/min 22.6`

- **含义**：`中位数/均值` = 每次进入该意图平均待多久（秒）。`switches/min` = 每个个体每分钟切换意图的次数。
- **怎么读**：驻留太短 = 状态机没起作用，还在每 0.2~0.5 s 重掷（0.2.x 的症状）；抖动太高 = 决策在相近分数之间来回跳。
- **阈值**：
  - 意图驻留**池化中位数 > 10 s**（P2 门禁 2；旧版 1–3 s）。
  - 抖动 **< 12 次/分钟/只**（P2 门禁 4）。
- **实现细节**：驻留用 0.25 s 分桶直方图统计，中位数精度 ±0.25 s；不保留逐次样本，所以 900 s 也不会吃内存。

### 3.3 路径长度 / 家园半径 / 方向性

`rabbit 2229  pathMed 44  homeRMed 8  homeRp90 20  netMed 14  dir 0.37`

- `n`：被统计的个体数，只算**存活 ≥ 10 s** 的个体（避免把刚出生的婴儿算进移动统计）。
- `pathMed`：一生累计移动距离（格）的中位数。单 tick 位移 ≥ 8 格视为瞬移（移民/读档）不计入。
- `homeRMed` / `homeRp90`：家园半径 = `max(经度跨度, 纬度跨度) / 2` 的中位数与 p90（格）。
- `netMed`：净位移（首末点直线距离）中位数。
- `dir`：**方向性** = `mean(净位移) / mean(路径长度)`。
  - `1.0` = 一直朝一个方向走；`0` = 纯随机游走。
  - **阈值 > 0.30**（P2 门禁 3）。
- **怎么读**：`path` 大而 `dir` 小 = 在原地打转（随机游走，0.2.x 的症状）；`dir` 高而 `homeR` 大 = 长距离定向迁徙；`dir` 高而 `homeR` 小 = 两点之间来回（觅食往返，通常是好现象）。

### 3.4 死因普查

`species  deaths  eaten starved old other | ageMed ageP10 ageP90 | source`

- **含义**：每个物种在整段观测里死了多少只，各死因多少。`ageMed/P10/P90` 是**死亡年龄**分布（秒），不是存活个体的年龄。
- `source` 列：`body.cause` = 引擎自己报的（可信）；`inferred:*` = 探针推断的（按 §6 打折）。
- **怎么读**：
  - `eaten` 高 = 捕食层在工作；`starved` 高 = 能量账本不闭合或食性/密度不对；
  - `old` 高 = 老死通道通（这是**健康**信号，说明动物能活到寿终）；
  - `other`/`unknown` 高 = **观测黑洞**，必须当 bug 查（`20-CORE-LOOP.md` 不变式 3：任何死亡都必须写入死因）。
- **阈值**：`starved` 占全部死亡 **< 50%**（P3 门禁，针对捕食层“不再全员饿死”）。
  - 注意语境：它是**捕食者层面**的验收。草食层饿死率高本身不违规，但见 §3.5。

### 3.5 饿死质量（P1 门禁 4 的度量）

`starvation quality: hunger at death median 0.32; 2684/3501 starved with hunger <= 0.6 (died on a full belly); 1554 starved while standing on grass with food under them`

- **含义**：只看 `cause=starved` 的个体：
  - `hunger at death`：死亡瞬间的饥饿度。**饿死就应该 hunger 高（接近 1）**。
  - `died on a full belly`：`hunger <= 0.6` 的饿死数。**这是最多的坏味道**。
  - `starved while standing on grass`：脚下有草（`grass > 0.02`）却饿死的数量。
- **阈值**（`90-ROADMAP.md` P1 门禁 4）：**不允许“站在草地上饿死”**，且饿死个体的 `hunger` 必须 `> 0.6`。
  - 即 `died on a full belly` 应为 **0**，`starved on grass` 应为 **0**。
- **为什么这条最重要**：它同时抓两个 bug——决策不读身体（`hunger` 与 `reserve` 脱钩），以及摄食门槛把可吃的草挡在外面。**任何一条不为 0，说明能量闭环还没通。**

### 3.6 年龄结构（期末）

`rabbit juv 36.9%  ad 58.6%  eld 4.5%   n=111`

- **含义**：观测结束那一刻，存活个体按幼年/成年/老年分。判定：`age < maturity` 为幼年，`age > maturity × 2.6` 为老年（与引擎 `stageOf` 同口径）。新引擎有 `body.M` 时以 `M < 1` 判幼年。
- **怎么读**：稳定种群通常**幼年占多数**（金字塔底宽）；`eld` 接近 0 且 `old` 死因为 0 = 没人活到老，说明寿命通道不通或是被吃光了。
- **陷阱**：`--seconds` 太短时**全物种都是幼年**（90 s 时狐/狼/鸦 100% juvenile），这是观测窗口太短，不是 bug。判年龄结构至少 300 s，900 s 更稳。

### 3.7 能量 × 饥饿散点

```
reserve  (row = body reserve 0..1, column = hunger 0..1)
0.9 |@:.................-
0.5 |=:::...............:
0.0 |.::::::.:..........-
    |--------------------  hunger
    fed           starving
```

- **含义**：每个实体-采样点，x = 饥饿度（右端最饿），y = 储备率（顶端最满）。字符密度按行内峰值做对数刻度（空格到 `@`）。
- **怎么读**：
  - 右上角（很饿但储备很满）应该是空区，否则 = 驱动力与身体脱钩。
  - 左下角（储备空却不饿）= §3.5 那个问题的可视化形态。
  - 正常图形应沿**对角线**分布：越饿储备越低。
  - 质量贴最左一列 = `hunger` 通道长期贴 0（0.2.x 症状：旧引擎 `needs.hunger` 被每次啃草重置，几乎永远是 0）。
- **阈值**：无硬门禁，但有形状要求：**主质量应落在对角带上**。若主质量在左下或右上，先查 `hunger` 派生规则（`20-CORE-LOOP.md` §2.2：`hunger = clamp(1 - E/Emax, 0, 1)`）。

### 3.8 生产者

`grass mean biomass 0.932   bare-cell share 1.4%`

- **含义**：草地/水面的平均生物量，以及裸地格占比（`biomass < 0.1`）。
- **怎么读**：`bare-cell share` 长期高位 = 草食层把草地啃穿（过牧）；长期 0 = 植物没被吃（食物链没接上）。旧测试要求植被覆盖率 ≥ 3%。

|---|---|---|---|
| P1-5 | 吞吐 | ≥ 30 ticks/s @ 3000 实体 | 90-ROADMAP P1 |
| P1-4 | 饿死质量 | `hunger>0.6`，且 0 例“站在草地上饿死” | 90-ROADMAP P1 |

## 5. 读数陷阱（按顺序看）

1. **bundle 是 stale 的**：报告头带 `STALE` 就先 `node tools/build-client.mjs`，否则你测的是旧代码。
2. **两条报告 seed 不同**：不可比。生态模型对初始条件极敏感，峰值差几倍是常态。
3. **`--seconds` 太短**：年龄结构全幼年、`old` 死因为 0、迁徙还没发生。判行为至少 300 s，判季节/年龄要 900 s 以上。
4. **移民开着**：`--no-immigration` 关掉后灭绝是**允许出现**的，因为安全网本来就在兜底。只有测“链路自持”才关它。
5. **`spawned` 的口径**：`spawned` 不含开局建群个体（报告里单列 `start`）。`+2151 (2133 born)` = 2151 个新个体，其中 2133 个是 `generation > 1` 的真出生，差的 18 个是移民。**移民和出生必须分开看**。
6. **旧引擎的 `hunger` 通道**：`needs.hunger` 和 `reserve` 是两个独立变量，`needs.hunger` 长期贴 0。不要拿它当“它饿不饿”的判据——这正是 §3.5 要抓的东西。
7. **死因是推断的**（旧引擎）：见 §6，`inferred:*` 的可信度不是 100%。

## 6. 死因判定：先测什么、再推什么

新引擎（有 `body.cause`）：**直接用引擎的**。`20-CORE-LOOP.md` 不变式 3 要求任何死亡都写入 `body.cause`（`starved`/`frozen`/`predation`/`old`/`disease`），探针只做汇总。

旧引擎（没有 `body.cause`）：探针按**固定顺序**推断，顺序不能改：

| 顺序 | 判据 | 结论 |
|---|---|---|
| 1 | `fate === 'eaten'` | `predation` |
| 2 | `age > lifespan - 2` | `old` |
| 3 | 死亡瞬间 `reserve === 0` 且死前 `> 0` | `predation`（捕食者把 `victim.energy` 归零） |
| 4 | 死亡瞬间 `reserve < 0` | `starved`（饿死是负残值，不是精确 0） |
| 5 | 其他 | `unknown`（**观测黑洞，当 bug 查**） |

> 为什么第 2 步必须在第 3 步之前：老死的个体 `reserve` 是正的，如果先判“能量 ≤ 0 就是饿死”，老死会被误记成饿死——第一轮诊断里踩过这个坑。
> 为什么第 3、4 步要区分 `=== 0` 和 `< 0`：捕食路径是 `victim.energy = 0`（精确归零），饿死路径是 `energy -= drain*dt`（浮点负残值）。两者撞上的概率极低，但不是 0。

**校准方法**（量的是探针自身精度，不是引擎）：把 `client.js` 在内存里打补丁，让 `killEntity` 记录动物**死前**的 `fate/energy/age`，再与探针推断逐 id 比混淆矩阵。补丁只存在于临时脚本里，**不进仓库**；探针永远度量未打补丁的 bundle。

## 7. before / after 标准流程

```powershell
# 1) 改之前（先保证 bundle 已构建）
node tools/build-client.mjs
node tools/behaviour-probe.mjs --seed 12345 --seconds 900 --json > D:/tmp/probe-before.json

# 2) 改之后
node tools/build-client.mjs
node tools/behaviour-probe.mjs --seed 12345 --seconds 900 --json > D:/tmp/probe-after.json
```

提交说明里贴：
- 两条报告的 `bundleHash`（不同就要说清为什么）；
- 门禁那一节的 PASS/FAIL 变化；
- §3.5 饿死质量的三个数（最敏感的指标）。
